# dxdb-vectors

Typed reader for the cross-language oracle vectors in `testdata/vectors/`.

The `*.json` files there are generated by running real upstream RxDB in Node
(`xtask/vectors/`, PLAN.md section 7.2). They are the specification this port is
tested against. This crate is the only supported way to read them.

## Load and iterate a family

This is the whole pattern. Copy it.

```rust,no_run
use dxdb_vectors::{schema_hashes, VectorFamily, Vectors};

let vectors = Vectors::discover();               // resolves testdata/vectors/ for you
let hashes = vectors
    .load::<schema_hashes::Vectors>(VectorFamily::SchemaHashes)
    .expect("the committed vectors decode");

for case in &hashes.cases {
    // `input` is the schema as upstream's fixture declares it, key order preserved.
    let filled = dxdb_schema::fill_with_default_settings(&case.input).unwrap();
    assert_eq!(filled.hash(), case.hash.as_deref().unwrap(), "{}", case.name);
}
```

`Vectors::discover()` resolves the directory from *this* crate's manifest dir, so it
works from any consumer crate at any nesting depth. Do not build the path yourself;
six files used to, and they all spelled it slightly differently.

## What you do not have to do

| instead of | use |
| --- | --- |
| `concat!(env!("CARGO_MANIFEST_DIR"), "/../../testdata/vectors/x.json")` | `Vectors::discover().path(family)` |
| `serde_json::from_str::<Value>(&text)` then `["cases"].as_array()` | `vectors.load::<family::Vectors>(family)?.cases` |
| `case["schema"].as_str()` then a local `HashMap` of schemas | `schema_hashes.fixture_input(name)` |
| copying a fixture schema literal into your test | `schema_hashes.fixture_inputs()` |
| `case["kind"].as_str() == Some("rejection")` | `index_strings::Vectors::refused()` |

`dxdb-schema`'s and `dxdb-query`'s test files used to carry a 40-line
`schema_lookup()` plus a hand-copied `averageSchema`; `fixture_inputs()` replaces
both.

## Reading provenance

```rust,no_run
use dxdb_vectors::{Provenance, VectorFamily, Vectors};

let vectors = Vectors::discover();
let p = vectors
    .load::<dxdb_vectors::jsnum::Vectors>(VectorFamily::Jsnum)
    .unwrap()
    .provenance();

assert_eq!(p.rxdb_commit.as_deref(), Some(Provenance::EXPECTED_RXDB_COMMIT));
```

`tests/provenance_pin.rs` anchors that constant to `NOTICE.md`, so a regeneration
against a different upstream fails instead of silently changing what you are checked
against.

## Case families

Each family is its own module with exact field names. `Vectors` is the top-level
document, `Case` is one entry.

- `jsnum`: `String(x)` / `JSON.stringify(x)` from Node.
- `index_strings`: index strings, declared lengths, bound helpers, and upstream's
  refusals (`refused()`).
- `schema_hashes`: hashes, the defaulted schema each covers, the relations, and the
  fixture schemas every other family refers to by name.
- `normalised_queries`: normalised queries, plans, sort orderings, matcher results.
- `bulk_write_categorization`: `categorizeBulkWriteRows` output, both directions.
- `selector_matching`: which documents match which selector, plus refusals.
- `replication_transcripts`: replicated state and checkpoints, step by step.

## The rules

1. **Do not edit a vector file.** Vectors are generated data. Editing one turns the
   oracle into a record of what we hope is true. Regenerate with `make vectors`.
2. **Do not work around a case you believe is wrong.** Report it with the family, case
   index and `why` label so the generator can be fixed and the file regenerated.
   Silently skipping a case shrinks the corpus and the suite keeps passing.
3. **Do not normalise the data.** Field names here match the JSON exactly, including
   `$comment`, `_deleted` and `$eq`. Renaming them would let a mismatch hide behind a
   translation layer.

Every struct denies unknown fields, so a generator change fails here loudly instead of
rendering a field invisible. If a load fails with `VectorError::Decode`, the generator
and this crate have to change together in one commit.

`tests/case_counts.rs` holds a committed expected case count per family, so a truncated
or replaced file cannot silently shrink the corpus your test runs against.
