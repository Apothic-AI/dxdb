## Order of work (do not reorder)

### 1. `dxdb-storage`: the traits

Port `RxStorage` / `RxStorageInstance` faithfully
(`src/types/rx-storage.interface.d.ts:116`). PLAN.md 4.2 lists the contract:

- `bulk_write(rows, context)`: **per-document atomic, no cross-document
  transaction, partial success with a per-row error list.** This is load-bearing;
  the retry and conflict logic above it assumes it.
- `find_documents_by_id(ids, with_deleted)`, `query(prepared)`, `count(prepared)`,
  `get_attachment_data(doc_id, att_id, digest)`.
- `get_changed_documents_since(limit, checkpoint)` — optional upstream, with a
  documented fallback. Two of the eight instance methods are optional; do not make
  them required.
- `change_stream()`.
- `cleanup(minimum_deleted_time) -> bool`, where `false` means "more work remains,
  call again".
- `close()`, `remove()`.

Also port **`categorizeBulkWriteRows`** (`src/rx-storage-helper.ts:205`) as a
**single well-tested pure function** with the same inputs and outputs — not as
scattered logic. PLAN.md 4.3: it is where insert / update / conflict /
same-state-fork decisions are made, and it is "the heart of RxDB's consistency
story". Lane C is generating `testdata/vectors/bulk-write-categorization.json` for
exactly this; consume it when it appears, and use
`make gate-storage` / `make gate-query-correctness` as the gates.

Async trait strategy per PLAN.md 3.3: `-> impl Future` where the concrete type is
known; a `dyn`-safe mirror generated by `dynosaur` (already in
`[workspace.dependencies]`) where the wrapper stack needs a trait object. Use
`futures::Stream` for change streams and query results. **Do not leak RxJS.** No
`async_trait` in hot paths.

### 2. `dxdb-memory`: the parity oracle

A real indexed in-memory storage, not a stub. Comparison of whole index strings
uses **code-unit order** (`dxdb_jsstr`), because that is what
`memory-helper.ts:337` `compareDocsWithIndex` does.

### 4. `dxdb-core` and `dxdb-reactivity`

CRUD, bulk operations, revisions, conflict categorisation, the document cache,
change events, hooks, live queries, the write queue.

**Revisions are `{height}-{databaseInstanceToken}`** (`utils-revision.ts:59`). Not
a content hash, not a UUID, not a vector clock. Height is 1 for a new doc,
`previous + 1` after. `parseRevision` accepts multi-digit heights. Compare heights
via `get_height_of_revision` without allocating.

Reactivity: change-event buffer, event reduce, live-query windows
(`src/change-event-buffer.ts`, `src/event-reduce.ts`, `src/query-cache.ts`,
`src/rx-change-event.ts`).

Hooks: upstream mutates five prototypes at plugin-add time (`src/plugin.ts:35`)
and exposes 24 named hooks (`src/hooks.ts`). Rust has no prototype mutation. Use
the re-expression in PLAN.md 4.3: a `Hooks` registry owned by the database with
explicit ordering and the same hook names.

## Non-negotiable rules

- `dxdb-core` **never** depends on a storage crate. It depends on `dxdb-storage`
  traits. `dxdb-memory` is the only storage allowed in `dxdb-core`'s
  dev-dependencies.
- Numbers that become strings go through `dxdb-jsnum`. String sort/comparison goes
  through `dxdb_jsstr`.
- Every crate builds for `wasm32-unknown-unknown`. No `tokio` in the core: it
  compiles for wasm but its timers and IO do not work there. Use `futures` and let
  the platform binding supply the executor.
- No `unsafe`.

  monotonic revisions, no lost writes, `count` equals `query().len()`.

## Scope discipline

No replication, no browser storages, no plugins, no JS bindings. Those are other
lanes. Implement the minimum trait surface that makes the conformance suite
meaningful, then make the suite pass.
