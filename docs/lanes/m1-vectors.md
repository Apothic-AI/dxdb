# Lane brief: oracle vectors

You own `xtask/vectors/` and `testdata/vectors/`. Your job is to make
"behaviourally identical to RxDB" an assertable claim instead of an aspiration, by
running real upstream RxDB in Node and committing its observable output as JSON.

## Read first

1. `docs/PLAN.md` section 7.2 — this brief is that section, made concrete.
2. `docs/GATES.md` tier 2.
3. `docs/WORKTREES.md` — you own `xtask/vectors/` and `testdata/vectors/` only.
   Do **not** edit `xtask/src/`, `xtask/status.py`, `xtask/Cargo.toml`, or the
   Makefile (leader-owned).

Upstream is checked out at `~/Code/rxdb` (pin `3b763ee17`, v17.6.0). You may read
it and you may `npm install` **inside the worktree of your own lane**, but never
modify the upstream checkout: it is other lanes' reference.

## Existing pattern to follow

`xtask/vectors/jsnum.mjs` is the reference implementation of this pattern. Read it
first. It: computes vectors from real JS, dedupes, stores the double as a string so
both sides parse identical bits, writes `testdata/vectors/<family>.json`, and
supports `--check` for CI drift detection. Every new family follows the same shape,
the same `$comment` header discipline, and the same `--check` contract.

`make vectors` runs `node xtask/vectors/generate.mjs`, which must exist and run
every family. Right now that file does not exist; create it as a dispatcher that
runs each family module and honours `--check`.

## Families to build, in this order

1. **`index-strings.json`.** For every schema/field/value combination in upstream's
   fixtures, the index string RxDB produces. Source: `src/custom-index.ts`
   (`getIndexableStringMonad`, `getNumberIndexString`). Include the clamping cases
   at and beyond the schema-declared min/max, because that boundary is where a
   reimplementation goes wrong silently.
2. **`schema-hashes.json`.** Schema hash for every fixture schema, including the
   meta-injected ones. This pins `rx-schema-helper.ts`'s defaulting and hashing.
3. **`normalized-queries.json`.** Normalised query output for a generated corpus:
   sorts, the primary key appended when absent, a `desc` triggering re-sort, the
   planner's `startKeys`/`endKeys`/`selectorSatisfiedByIndex`, and `INDEX_MIN`'s
   JSON round-trip.
4. **`bulk-write-categorization.json`.** `categorizeBulkWriteRows`
   (`src/rx-storage-helper.ts:205`) outputs for generated write sequences. This is
   the heart of RxDB's consistency story; PLAN.md 4.3 requires it be ported as a
   single pure function, and this vector file is how we prove the port.
5. **`replication-transcripts.json`.** A scripted pull/push sequence in, the
   resulting checkpoints and resolved document states out. Feeds M3.
6. **`selector-matching.json`.** For a generated corpus of documents and selectors,
   which documents match. This is the differential oracle for the M1 matcher and
   the property test in M1 consumes it.

Each family: a deterministic generator (fixed seed, no `Math.random()` without a
seeded PRNG), a bounded case count (hundreds, not millions — this is committed
data), and a `--check` mode.

## Constraints

- **Deterministic output.** Two runs on the same Node version must produce
  byte-identical files. Sort keys explicitly; never rely on object iteration order
  for a list whose order is not semantic.
- **No committed `node_modules`.** Add an ignore rule if you need one; the
  `.cargo-remote-3000.toml` exclude list already covers `node_modules/` so remote
  builds do not upload it.
- **Vectors are data, not code.** A consumer crate reads them with `serde_json`
  from `testdata/vectors/`. Do not generate Rust source.
- **Node version in the file is informational.** `--check` must not fail just
  because Node was upgraded, if the numbers are identical. `jsnum.mjs` shows how.
- If upstream RxDB cannot produce a family without writing to disk or opening a
  storage, use the in-memory storage; if it still needs a browser API, say so in
  your report instead of faking the data.

## Your gate

```bash
make vectors          # regenerates every family
make vectors-check    # exits 0 when committed vectors match Node's current output
git status --short testdata/  # must be clean after `make vectors` (idempotent)
```

Report: one line per family with its case count, the total committed bytes, and
any family you could not build and why.

## Why this matters

PLAN.md 7.2: "A drift in either implementation shows up as a data diff, not a
mystery test failure. This is what makes the claim assertable." A vector file that
was generated by our own Rust code would be worthless; it must come from Node
running upstream RxDB.
